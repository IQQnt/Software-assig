Cuestionario guía

1. ¿Qué diferencia hay entre un programa y un producto de software?

Un programa es un conjunto de instrucciones escritas en un lenguaje de programación que le indican a la computadora qué hacer. Es la parte puramente lógica y funcional.

Un producto de software es mucho más amplio: incluye el programa, pero también los datos que maneja, la documentación (manuales, especificaciones, diagramas), los procedimientos de instalación y uso, y el soporte. Es decir, un producto de software es un paquete completo listo para ser usado por alguien, mientras que un programa es solo una pieza de ese paquete.

2. ¿Por qué se dice que el software "no se desgasta" pero sí se deteriora?

El software no se desgasta porque no es un objeto físico: no tiene piezas que se rocen, se oxiden o se rompan con el uso. Un programa puede ejecutarse infinitas veces sin perder material.

Pero sí se deteriora porque el entorno cambia (nuevos sistemas operativos, nuevas necesidades del usuario, nuevos requisitos legales) y el software no se adapta solo. Además, cada modificación sin control (parches, cambios apresurados) va acumulando complejidad y errores, haciendo que el software pierda calidad con el tiempo. Por eso necesita mantenimiento constante.

3. ¿Qué lugar ocupa el software dentro de un sistema de información?

El software es uno de los cinco componentes de un sistema de información, junto con el hardware, los datos, las personas y los procedimientos. No es el sistema completo: es el componente que procesa y transforma los datos para que las personas puedan tomar decisiones o realizar tareas. Sin las personas que lo usan y los procedimientos que lo rodean, el software por sí solo no constituye un sistema de información útil.

Justificación de las dos notas más bajas (Robustez = 2 y Mantenibilidad = 2)

Robustez (2): Si el estudiante ingresa un dato inválido en el formulario de inscripción (por ejemplo, una cédula con letras o un correo sin formato correcto), el sistema no muestra un mensaje claro de error: se queda cargando o lanza una pantalla de error genérica. Eso indica que no maneja bien las entradas inesperadas.

Mejora propuesta: Implementar validaciones en el formulario con mensajes específicos ("La cédula debe contener solo números") y manejar los errores del servidor con páginas amigables en lugar de mensajes técnicos.

Mantenibilidad (2): Cuando la universidad cambia una regla de inscripción (por ejemplo, el número máximo de materias por semestre), el sistema tarda semanas en actualizarse porque la lógica está dispersa en muchos archivos y sin documentación. Eso indica que es difícil de modificar.

Mejora propuesta: Centralizar las reglas de negocio en un solo módulo, documentar el código y usar un repositorio con control de versiones para facilitar los cambios futuros.

Cuestionario guía

1. ¿Cuál es la diferencia entre cualidades internas y externas? Da un ejemplo de cómo una interna produce una externa.

Las cualidades externas son las que percibe el usuario al usar el software: usabilidad, confiabilidad, eficiencia, etc. Las cualidades internas son las que percibe quien construye o mantiene el software: mantenibilidad, reutilización, claridad del código, modularidad.

Ejemplo: Un código bien modularizado y documentado (cualidad interna: mantenibilidad) permite corregir un fallo rápidamente; el usuario final percibe esa corrección como un sistema más confiable (cualidad externa).

2. ¿En qué se diferencian corrección y robustez?

La corrección se refiere a que el software hace lo que se especificó cuando recibe entradas válidas y se usa como se espera. La robustez se refiere a cómo responde el software ante entradas inválidas o situaciones inesperadas (un dato mal escrito, un archivo corrupto, una conexión que se cae).

Un sistema puede ser correcto (cumple los requisitos en condiciones normales) pero poco robusto (se cae o muestra errores feos cuando algo sale mal). Lo ideal es que sea ambas cosas.

3. ¿Qué cualidad sería prioritaria en un sistema para una comunidad con computadores antiguos y conexión limitada? ¿Por qué?

La eficiencia (uso adecuado de recursos: tiempo, memoria, red) y la portabilidad (que funcione en distintos equipos y sistemas operativos).

En equipos antiguos, un software que consuma mucha memoria o que requiera conexión rápida será inutilizable. La eficiencia garantiza que funcione con recursos modestos, y la portabilidad asegura que no dependa de un sistema operativo moderno que la comunidad no puede costear. También la usabilidad es clave, porque usuarios con poca experiencia técnica necesitan interfaces simples.

Tema 3. Factores de calidad del software

Cuestionario guía

1. ¿Qué es un factor de calidad y en qué se diferencia de una cualidad?

Un factor de calidad es un criterio medible que se usa para evaluar y controlar la calidad del software a lo largo de su vida útil (por ejemplo, corrección, fiabilidad, mantenibilidad, portabilidad). Se agrupan según el momento del ciclo de vida: operación, revisión y transición.

Una cualidad es una característica o propiedad del software que determina qué tan bien cumple su propósito. La diferencia es de enfoque: la cualidad describe qué propiedad tiene el software (usabilidad, seguridad), mientras que el factor de calidad es el criterio de medición y control que se aplica para evaluar esa propiedad durante el proceso. En la práctica, los términos se usan de forma cercana, pero el factor de calidad tiene una connotación más de gestión y medición.

2. ¿Por qué conviene detectar los errores en las primeras fases?

Porque el costo de corregir un error crece exponencialmente con el avance del proyecto. Un error en los requisitos detectado en la fase de análisis se corrige con una conversación y un ajuste en el documento. Ese mismo error detectado en producción implica rehacer diseño, código, pruebas, capacitación y hasta compensar a los usuarios afectados. McConnell (1999) insiste en que revisar requisitos y diseño ahorra mucho más que probar al final.

3. ¿Qué propone Humphrey para mejorar la calidad desde el trabajo individual?

Humphrey propone el Proceso Software Personal (PSP): que cada persona defina, mida y mejore su propio proceso de trabajo. En concreto, sugiere medir el tiempo que se dedica a cada tarea y registrar los defectos propios (qué error cometió, en qué fase, cuánto tardó en corregirlo) para identificar patrones y mejorar continuamente. La calidad del producto depende de la calidad del proceso y del trabajo de cada individuo.

4. Elige un factor de cada momento (operación, revisión, transición) y da un ejemplo de un sistema que lo cumpla o lo incumpla.

Operación – Fiabilidad: Un sistema de facturación de condominio que lleva meses funcionando sin caerse y sin perder pagos registrados cumple la fiabilidad. Si un día se cae y pierde los pagos validados del día, la incumple.

Revisión – Mantenibilidad: Un sistema cuyo código está modularizado y documentado permite cambiar la regla de cálculo de la cuota en un día. Si el código está disperso y sin documentación, cambiarla tarda semanas: incumple la mantenibilidad.

Transición – Portabilidad: Un sistema de facturación que corre igual en Windows, Linux y en un navegador web cumple la portabilidad. Si solo funciona en una versión específica de Windows, la incumple.

Tema 4. Ingeniería del software

Práctica

"¿Se puede hacer buen software solo con talento y sin método?" Redacta una conclusión de máximo 150 palabras.

No. El talento es valioso, pero por sí solo no garantiza buen software. Un programador talentoso puede escribir código brillante para un problema pequeño, pero cuando el proyecto crece (más requisitos, más usuarios, más cambios) la falta de método produce caos: código que nadie entiende, errores que aparecen tarde, plazos que se incumplen. La ingeniería del software nació precisamente de la "crisis del software": proyectos talentosos que fracasaron por falta de proceso. El método aporta planificación, documentación, control de cambios y verificación continua, que son lo que permite que el software sea mantenible y confiable en el tiempo. Talento sin método es improvisación; método sin talento es burocracia. Lo ideal es la combinación: talento guiado por un proceso disciplinado.

Cuestionario guía

1. ¿Qué problema dio origen a la ingeniería del software como disciplina?

La "crisis del software" de fines de los años sesenta: proyectos que se retrasaban, costaban mucho más de lo previsto y entregaban sistemas poco confiables, difíciles de mantener y que no satisfacían a los usuarios. La respuesta fue aplicar principios de ingeniería al desarrollo de software: procesos definidos, medición, documentación y control de cambios.

2. ¿Cuáles son los tres pilares de la ingeniería del software y qué aporta cada uno?

  • Procesos: definen qué actividades se hacen y en qué orden (análisis, diseño, construcción, pruebas, etc.). Aportan organización y repetibilidad.
  • Métodos: definen cómo se hacen técnicamente esas actividades (modelado, diagramas, técnicas de prueba). Aportan rigor técnico.
  • Herramientas: son el soporte que apoya las actividades (herramientas CASE, editores, repositorios, sistemas de prueba). Aportan eficiencia y automatización.

3. ¿En qué se diferencia programar de hacer ingeniería del software?

Programar es escribir código para que una computadora ejecute una tarea. Es una actividad técnica puntual, centrada en la construcción.

Hacer ingeniería del software es aplicar un enfoque sistemático, disciplinado y medible a todo el ciclo: identificar requisitos, analizar, diseñar, construir, probar, implantar y mantener. Incluye planificación, gestión de riesgos, documentación, control de cambios y verificación continua. Programar es una parte de la ingeniería del software, no su equivalente.

Tema 5. Visión general del proceso de desarrollo de software

Cuestionario guía

1. ¿Qué actividades comparten todos los procesos de desarrollo?

Independientemente de la metodología, todo proceso incluye: identificación del problema y requisitos, análisis, diseño, construcción (programación), pruebas, implantación y mantenimiento. Lo que cambia entre metodologías es cómo se organizan (secuencial, iterativo o ágil) y cuánto énfasis se pone en cada una, pero las actividades fundamentales siempre están presentes.

2. Compara las fases de Kendall & Kendall, Laudon & Laudon y O'Brien. ¿En qué coinciden?

Kendall & Kendall presentan siete fases del ciclo de desarrollo de sistemas. Laudon & Laudon hablan de análisis, diseño, programación, pruebas, conversión y producción con mantenimiento. O'Brien resume cinco etapas: investigación, análisis, diseño, implementación y mantenimiento.

Coinciden en el núcleo: todos incluyen análisis (entender el problema), diseño (planear la solución), construcción/implementación (hacerla realidad), pruebas (verificar que funciona) y mantenimiento (corregir y evolucionar). Las diferencias son de nombre y de granularidad: algunos separan más fases o agrupan otras, pero la esencia del proceso es la misma.

3. ¿Qué pasa si se omite el análisis y se pasa directo a programar?

Se construye un sistema que no responde a las necesidades reales del usuario. Sin análisis no se entiende cómo funciona hoy la organización ni qué debe hacer el sistema, así que se programa sobre suposiciones. El resultado típico: retrabajo constante, funcionalidades que nadie pidió, requisitos que aparecen tarde y un costo mucho mayor. Es la causa más común de fracaso de proyectos: se resuelve el problema equivocado con código correcto.

Tema 6. Participantes en el proceso de desarrollo de software

Cuestionario guía

1. ¿Quiénes son los stakeholders (interesados) de un sistema para una comunidad?

En el caso de un sistema de facturación de condominio, los stakeholders son:

  • Los condóminos: usuarios finales del historial y beneficiarios de la transparencia.
  • La junta de condominio / administración: cliente o patrocinador que solicita el sistema y define prioridades.
  • El miembro del comité que valida pagos: usuario operativo del sistema.
  • El equipo de desarrollo (ustedes tres): analistas, diseñadores, programadores y probadores.
  • El personal de mantenimiento o proveedores: indirectamente afectados por la transparencia en los gastos.

2. ¿Por qué el analista de sistemas se considera un puente entre usuarios y técnicos?

Porque el analista habla ambos idiomas: entiende el lenguaje del negocio (cómo trabaja la comunidad, qué necesita el comité) y el lenguaje técnico (modelos, bases de datos, arquitectura). Su función es investigar las necesidades reales, traducirlas en especificaciones claras que los programadores puedan implementar, y comunicar a los usuarios qué es viable y qué no. Sin ese puente, los técnicos construyen lo que creen entender y los usuarios reciben algo distinto a lo que pidieron.

3. ¿Qué riesgos hay cuando el usuario final no participa en el desarrollo?

Los riesgos principales son:

  • Requisitos equivocados: se construye lo que el equipo supone, no lo que el usuario necesita.
  • Rechazo del sistema: el usuario no lo adopta porque no se siente parte del proceso o porque la interfaz no le resulta familiar.
  • Retrabajo costoso: los errores se descubren al final, cuando corregirlos es más caro.
  • Pérdida de confianza: la comunidad siente que el sistema es impuesto y no responde a sus problemas reales.
  • Funcionalidades faltantes: necesidades obvias para el usuario pero invisibles para el equipo quedan fuera del alcance.

La participación del usuario debe ser continua, no solo al inicio y al final.

Actividad integradora de la Unidad 2 – Caso: Proyecto Socio-Tecnológico

Resumen de las respuestas del equipo para el proyecto de facturación de condominio.

1. El software: ¿qué tipo de software es y qué datos manejaría?

Es un Sistema de Procesamiento de Transacciones (TPS) con módulo de consulta/reportería. Captura, procesa y almacena los pagos de cuotas de condominio para generar facturas automatizadas, reduciendo la escritura manual. Aunque la validación del pago sea manual, el sistema sigue siendo transaccional porque registra, actualiza estados y persiste la información de forma íntegra.

Datos: condóminos (nombre, cédula, apartamento, contacto), transacciones (fecha, monto, referencia, estado, usuario validador), facturas (número correlativo, fecha, concepto, monto, datos fiscales) e historial de movimientos (descripción, categoría, monto, fecha, saldo).

2. Cualidades: las cinco más importantes y su orden

  1. Integridad: base de la confianza; un pago validado no se pierde ni se altera y la factura coincide con el monto verificado.
  2. Seguridad: control de acceso a datos financieros y personales; sin seguridad la integridad se compromete.
  3. Usabilidad: el validador del comité no es técnico; una interfaz simple evita errores humanos.
  4. Disponibilidad: el historial debe consultarse cuando la comunidad lo requiera.
  5. Mantenibilidad: el proyecto puede evolucionar (pasarelas de pago, nuevos reportes); el código debe ser claro y modificable.

3. Calidad: tres actividades de aseguramiento

  • Revisión de requerimientos y diseño (preventiva): revisar que el flujo pago → validación manual → factura → historial esté bien definido y sin ambigüedades antes de programar.
  • Pruebas de caja negra sobre el flujo transaccional (correctiva): casos de prueba para registrar pago, validarlo, verificar factura e historial, incluyendo casos de error (rechazo, corrección).
  • Auditoría de la base de datos (preventiva/correctiva): verificar que no haya facturas sin pago asociado ni discrepancias entre monto pagado y facturado.

4. Proceso: qué haría el equipo en cada actividad

  • Planificación: definir alcance, herramientas, cronograma y reparto de roles entre las tres integrantes.
  • Análisis y diseño: entrevistar (o simular) al administrador, modelar la base de datos y bocetar las pantallas de validación e historial.
  • Implementación: programar según el diseño; las otras dos revisan avances y preparan datos de prueba.
  • Pruebas: una simula al validador, otra al condómino y la tercera verifica la base de datos tras cada operación.
  • Despliegue: manual de usuario sencillo con capturas y presentación del sistema funcionando.

5. Participantes y qué se espera de cada uno

  • Equipo de desarrollo (ustedes tres): comprender el problema, diseñar, programar, probar y documentar; traducir la necesidad de transparencia en funcionalidad concreta.
  • Cliente / administración del condominio: explicar cómo se manejan hoy los pagos, qué datos debe llevar la factura y qué detalle quiere en el historial.
  • Usuario validador (miembro del comité): probar el software, dar retroalimentación sobre facilidad de uso y confirmar que el flujo es rápido y claro.
  • Condóminos: revisar el historial en la fase de pruebas y confirmar que la información es clara y comprensible.

6. Ciclo de vida: modelo seleccionado y argumento

Modelo de Prototipado (enfoque iterativo con prototipos).

  • Permite aclarar requisitos: mostrar prototipos de la pantalla de validación y del historial al cliente simulado permite refinar lo que realmente necesita, más efectivo que una especificación escrita.
  • Reduce el riesgo: detectar temprano si el historial no era lo esperado evita correcciones costosas al final.
  • Se adapta al equipo: para tres personas es más manejable construir versiones pequeñas y funcionales (primero registrar pagos, luego factura, luego historial) que abarcar todo de una vez.
